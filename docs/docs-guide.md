# ドキュメント運用ガイド

このプロジェクトの `CLAUDE.md` および `docs/` 配下を更新する際のルールを定めます。
新しいドキュメントを追加・既存ドキュメントを編集する前に必ず本ガイドを参照してください。

---

## 1. CLAUDE.md の記載ルール

`CLAUDE.md` は **Claude Code がセッション開始時に必ず読み込む** トップレベル指針集です。
記載すべき情報を厳選し、肥大化を防ぐことが最優先です。

### 1.1 記載するべき内容

- **言語ルール・コーディング規約のうち全タスク共通のもの**（例: 入出力は日本語）
- **セッション開始直後に必ず実行すべき手順**（例: タスク一覧の確認）
- **頻用コマンド**（環境構築・lint・型チェック・起動・ビルド）
- **見落とすと事故になる横断的な実装ルール**（例: スレッド間通信は Signal/Slot 経由）
- **ドキュメントマップ**（`docs/` 配下の主要ファイルへの導線）

### 1.2 記載しなくてよい内容

- 特定モジュール固有の実装詳細 → `docs/arch/{module}.md`
- 特定機能・画面の仕様 → `docs/spec/features/` または `docs/spec/screens/`
- ビルドの詳細・同梱バイナリ構成 → `docs/build.md`
- 進行中タスクの内容 → `docs/task/{slug}.md`
- 過去の調査・検討メモ → `docs/research/{topic}.md`
- コミット履歴・変更経緯（`git log` で十分なもの）
- 一時的な作業メモ（セッション内で完結する内容）

### 1.3 別ファイルに分けるべき判断基準

以下のいずれかに該当する場合は CLAUDE.md から外し、対応する `docs/` 配下に移します。

- **3行以上説明が必要な内容**（テーブル・コードブロック・手順など）
- **特定のモジュール / 画面 / 機能にスコープが限定される内容**
- **更新頻度が CLAUDE.md 全体より高い内容**（仕様変更で頻繁に書き換わるなど）
- **読むタイミングが「特定の作業時」に限定される内容**（毎セッション必要ではないもの）

CLAUDE.md には概要 1〜2 行と詳細ファイルへのリンクのみを残します。

### 1.4 CLAUDE.md 更新時の手順

1. 追加内容が 1.3 の基準に該当するかを確認
2. 該当する場合は `docs/` 配下に新規/既存ファイルを編集し、CLAUDE.md にはリンクのみ追記
3. ドキュメントマップ表を更新（必要な場合）

## 2. docs/ 配下のフォルダ構成と追加基準

### 2.1 現行のフォルダ構成

| フォルダ / ファイル | 用途 | 命名規則 |
|---|---|---|
| `docs/spec/` | 製品の **動作仕様・画面仕様**（"何が起きるか"） | `kebab-case.md` |
| `docs/spec/features/` | 機能単位の仕様（キュー・ダウンロード形式 等） | `kebab-case.md` |
| `docs/spec/screens/` | 画面単位の仕様（ダイアログ・パネル 等） | `kebab-case.md` |
| `docs/arch/` | `yt_gui/` 各モジュールの **実装詳細**（"どう実装されているか"） | `snake_case.md`（モジュール名と一致） |
| `docs/task/` | 進行中・未着手タスクの管理（`index.md` + 作業中の `{slug}.md`） | `kebab-case.md`（タスク slug） |
| `docs/task/archive/` | 完了タスクのアーカイブ（テーマ別 `index.md` + 完了済み `{slug}.md`） | `kebab-case.md`（タスク slug） |
| `docs/research/` | 採否未決の **調査・検討メモ**（実装前の比較検討など） | `kebab-case.md` |
| `docs/testing/` | テスト方針・実行コマンド・カバレッジ運用 | `kebab-case.md` |
| `docs/build.md` | PyInstaller ビルド・同梱バイナリ | 直下の単独ファイル |
| `docs/git-workflow.md` | ブランチ運用・Issue ベース開発・PR の詳細ルール | 直下の単独ファイル |
| `docs/docs-guide.md` | 本ガイド | 直下の単独ファイル |
| `docs/harness-retro-log.md` | ハーネス見直し（git-workflow §5.9・`/harness-retro`）の回ごとの記録 — 窓・候補表・採否・メモリ整理の前後。採否が決まった後も追記し続けるログなので `docs/research/` には置かない | 直下の単独ファイル |

### 2.2 既存フォルダにファイルを追加する基準

- **`docs/spec/features/`**: 新しい機能（ユーザーから見える振る舞い）を追加・大幅変更したとき
- **`docs/spec/screens/`**: 新しい画面・ダイアログ・パネルを追加したとき
- **`docs/arch/`**: `yt_gui/` 配下に新しいモジュールを追加したとき。**ファイル名は `{module_name}.md` でモジュール名に一致させる**
- **`docs/task/`**: 新規タスク発生時に `{slug}.md` を作成し、`docs/task/index.md` にも追記
- **`docs/research/`**: 実装に着手する前の調査・選定メモを残したいとき（採否が決まり実装に入った後は spec/arch に正式版を書く）

### 2.3 新規フォルダを追加する基準

新規フォルダの追加は **既存カテゴリに収まらない明確な理由がある場合のみ** 行います。
迷ったときは既存フォルダ直下にファイルを置くか、`docs/` 直下に単独ファイルを作成してください。

新規フォルダ追加が妥当な例:
- 横断的な新カテゴリ（例: テスト戦略一式 → `docs/testing/`）が複数ファイルに渡って必要になったとき
- 既存フォルダの 1 ファイルが肥大化し、サブカテゴリに分割したほうが見通しが良くなるとき

新規フォルダを追加した場合は **必ず本ガイド (2.1 表) と CLAUDE.md のドキュメントマップを更新** してください。

## 3. docs/ 内ファイルの記載ルール

### 3.1 共通ルール

- **言語**: 日本語で記述（CLAUDE.md の言語ルールに従う）
- **見出し**: H1 はファイル先頭に 1 つだけ。H2 以下で構造化
- **表を活用**: 列挙的な情報（フィールド一覧・シグナル一覧・コマンド一覧 等）は箇条書きより表で
- **コードブロック**: 言語指定を必ず付ける（` ```bash `, ` ```python ` など）
- **冗長な散文を避ける**: 1 セクション 1 主題、簡潔に

### 3.2 種別ごとの記載内容

#### `docs/spec/` — 仕様

**書くべきこと**
- ユーザーから見える振る舞い・画面要素・操作フロー
- 入力と出力の関係、デフォルト値、設定項目の意味
- 機能間の依存関係

**書かないこと**
- クラス名・関数名・実装手段（→ `arch/`）
- 「なぜこの実装にしたか」の経緯（→ コミットメッセージ or `research/`）

#### `docs/arch/` — 実装

**書くべきこと**
- モジュールが提供するクラス・関数の概要と責務
- シグナル / スロット定義、初期化順序、スレッド境界などの **コードを読むだけでは見落としやすい不変条件**
- 関連する仕様ファイルへのリンク（先頭に `> 関連仕様: [...](../spec/...)` 形式で記載）

**書かないこと**
- 全関数の網羅的な API リファレンス（コードと docstring で十分なもの）
- ユーザー向けの振る舞い説明（→ `spec/`）
- 実装の行単位の解説

#### `docs/task/` — タスク

**書くべきこと**
- タスクの背景・ゴール・完了条件
- 関連ファイル・関連仕様へのリンク
- 進捗（**受け入れ条件ごとに 1 行 + `証跡:`**。下の「進捗欄と訂正ログ」）と訂正ログ

**書かないこと**
- 仕様や実装の正式説明（→ 完了時に `spec/` / `arch/` に転記）

**タスクメモの見出し規約**: [SessionStart hook](../.claude/hooks/session_task_status.py) は `docs/task/index.md` の `## タスク` 表で `進行中` のメモを開き、次の 3 つを注入する。見出しの語と注入量の上限は hook の定数（`NEXT_KEYWORDS` / `PROGRESS_PREFIX` / `PER_MEMO_LIMIT` / `TOTAL_LIMIT`）が正本で、ここには**書き方の約束だけ**を置く（上限の行数をここに写さない — 片方だけ直る事故の元）。

| 注入するもの | メモ側の書き方 |
|---|---|
| 冒頭の引用ブロック | 本文先頭から最初の `## ` までの、連続する `> ` 行（Issue・ステータス・ブランチ・基点）。空行を挟むとそこで切れる |
| 申し送り | H2 見出しに「次にやること」または「申し送り」を**含む**節（例: `## 次にやること（申し送り・YYYY-MM-DD 時点）`）。複数あれば文書順に全部 |
| 未完了項目 | H2 見出しが「進捗」で**始まる**節（例: `## 進捗（受け入れ条件 = …）`）の `- [ ]` / `* [ ]` 行だけ（入れ子も含む） |

節は H2 単位（次の `## ` まで、H3 以下は内包）。注入はメモごと・合計に上限があり、超えた分は「…以下は <path> を読む」で切られるので、申し送りは**再開に要ることだけ**を上に書く。**セッションを分ける前に「次にやること」を更新する**（[git-workflow.md](git-workflow.md) §5 の分割点 A / B）。メモが読めない・節が無い・チェック項目が無い・未チェック 0 件は hook がそれぞれ別の 1 行で知らせる（「無い」と「全部済んだ」を同じ文にしない）。

**進捗欄と訂正ログ**: 進捗欄が段階（investigate・設計・実装・docs・evaluator）の羅列になると、実際に時間を食った自己訂正がどこにも項目にならず、リストは静止したまま作業だけ増える。形は次のとおり（機械検査はしない。規約として守る）。

| 節 | 書き方 |
|---|---|
| `## 進捗…` | 項目は **受け入れ条件 1 つ + ` — 証跡: ` + 証跡のパス（未完なら `未`）**（例: `- [ ] C1 注入内容 — 証跡: 未`、完了時は `- [x] C1 注入内容 — 証跡: tests/test_x.py・変異 5 件`）。**段階（「実装」「docs 更新」「evaluator」）を項目にしない** — Issue の受け入れ条件に無い限り書かない。**例外は verify-gate の 1 行だけ**（結果を 1 行にまとめ、それも `証跡:` を付ける）。**箇条書きで書く**（表形式にしない — チェックボックス行が無いと hook が未完了項目を拾えない）。`[x]` にするとき `証跡: 未` のままにしない |
| `## 訂正ログ` | **必須**（固定の見出し。「進捗」で始まらず「次にやること」「申し送り」を含まない独立 H2 — hook に吸われない）。表の列: **日付 / 何を誤って書いたか / 正しくは / どの検査・手順なら捕まえたか**。空でも見出しと表ヘッダは置く。載せるのは**書いた主張が誤りだった件**（自己訂正・無効になった測定の主張）で、外部要因による誤りでない手戻りは載せない。**evaluator の指摘は載せない**（評価ゲートの巡回はタスクメモの巡回表が正本で、git-workflow §5.2「止め時の規則」で止まる。訂正ログにも数えると二重に止まる）。自己訂正のコミット（件名に「訂正」「偽の」「外れた」等）を作るときは**同じコミットで 1 行足す** |
| `## 次にやること…` | 末尾に **`訂正ログ: N 件`** の 1 行を必ず持つ（hook は `## 訂正ログ` を注入しないので、`/clear` をまたいでも件数が再開時に届くように。止まった日付があれば `（止まった: YYYY-MM-DD）` を添える） |
| 止め規則 | 訂正ログが **2 件**になったら次の作業に入る前に止まる（3 件目以降も毎回）。正本は [git-workflow.md](git-workflow.md) §5.2「訂正ログの止め規則」 |

> この形は #326（2026-09）で入れた。それより前のタスクメモ（archive を含む）は自由形式のまま置いておく（書き直さない）。進行中のまま残っている旧形式のメモは、hook が「節が無い」と知らせるので、次に触るときに直す。

`docs/task/index.md` のステータス（未着手 / 進行中 / 完了）と更新日は **タスク状態が変わるたびに必ず更新** してください。

**`docs/task/index.md` は短く保つこと。** このファイルはセッション開始時に毎回読み込まれ（[git-workflow.md](git-workflow.md) §5.6 の SessionStart hook が 2 つの表と、`進行中` メモの申し送り・未完了項目を注入する）、内容がそのまま文脈コストになります。置いてよいのは次の 2 つの表だけです。

| 表 | 内容 |
|---|---|
| `## タスク` | タスクメモ（`docs/task/{slug}.md`）を持つ進行中・未着手のタスク |
| `## 起票済み・未着手の Issue` | メモをまだ作っていない（着手時に作る）未着手の Issue |

**完了したタスクの経緯・分割の理由・着手時の申し送りは [`docs/task/archive/index.md`](task/archive/index.md) の「完了タスクの経緯・申し送り」へ書きます**（`docs/task/index.md` には書かない）。未着手 Issue の行からその節へリンクして導線を保ってください。表の見出し（`## タスク` / `## 起票済み・未着手の Issue`）は hook が抽出のキーにしているため、改名する場合は [`session_task_status.py`](../.claude/hooks/session_task_status.py) も合わせて直します（見出しが見つからない場合は、表の代わりに見つからなかった旨を 1 行注入する。[git-workflow.md](git-workflow.md) §5.6）。

#### `docs/research/` — 調査メモ

**書くべきこと**
- 調査の目的・前提・選択肢・比較表・結論
- 採用しなかった案とその理由

**書かないこと**
- 採用後の正式仕様（→ `spec/` に書く）
- 古くなった情報の放置（採否確定後に陳腐化したものは削除または明記）

### 3.3 リンクと参照の整合

リンクだけでなく、**本文が他の記述を指している関係**すべてを対象にします（語彙・名前も「概念への参照」です）。

- **相対パス**で記載する（`[ダウンロード形式](../spec/features/download-formats.md)` など）
- **`arch/` の各ファイル先頭**（目次の `index.md` を除く）には `> 関連仕様: [タイトル](../spec/...)` を必ず置く。利用者から見える振る舞いを持たない内部モジュール（エントリーポイント・共通ヘルパなど）で対応する spec が無いときは、`> 関連仕様: なし（<理由>）` と書く（行ごと省くと、付け忘れと区別できない）
- **`spec/` の index** からは対応する画面/機能ファイルへ表でリンク
- **`arch/index.md` の表** には対応する `spec/` ファイルを「関連仕様」列で併記
- ファイル名を変更・移動したときは **被リンク元を grep で確認** して更新する
- **名前・語彙を変えたときも同じく grep で洗う。** リンクは張り替えられても、**その語を使って書かれた説明文**が古いまま残ります。**リンク切れと違って読んでも気づきにくく、次に読む人を誤った方向へ導きます**（実運用のプロジェクトでは、1 つの概念を改名した 1 PR で**同じファイルの別の節に 11 箇所・コード内コメントに 15 箇所以上**残り、**うち 1 つは直下の実装と正反対の説明**になっていました）。
  - **洗う範囲は `docs/` に限りません。** 実装・テスト・E2E のコメント、テスト名、ログの文言も対象です。
  - **テストにはできません。** 「以前は〜だった」という**経緯の記述は正しい**ので、旧語を機械的に禁止すると誤検出になります。**残っているものが「現在の説明」か「経緯の記録」か**は読んで判断します。

### 3.4 index.md の運用

各サブフォルダに `index.md` を置き、**そのフォルダ内の全ファイルへの導線** を表形式で提供します。
ファイルを追加・削除・改名したら **必ず同フォルダの index.md を更新** してください。

## 4. コード変更時のドキュメント連動更新

CLAUDE.md にも記載のとおり、**コードまたは仕様を変更・拡張するときは対応する `docs/spec/` / `docs/arch/` を必ず併せて更新** してください。

### 4.1 変更箇所別の更新先

| コード変更内容 | 更新が必要なドキュメント |
|---|---|
| 新しい画面・ダイアログ追加 | `docs/spec/screens/{name}.md` 新規 + `spec/index.md` 追記 + `arch/{module}.md` 新規 + `arch/index.md` 追記 |
| 新しい機能追加 | `docs/spec/features/{name}.md` 新規 + `spec/index.md` 追記 + 関連 `arch/` 更新 |
| 既存機能の振る舞い変更 | 該当 `docs/spec/features/{name}.md` を更新。実装が大きく変わったら `arch/` も |
| 新モジュール追加 (`yt_gui/{name}.py`) | `docs/arch/{name}.md` 新規 + `arch/index.md` 追記 |
| 設定項目追加・変更 | `docs/spec/settings.md` + `docs/arch/settings.md` |
| 新言語追加 | `docs/spec/i18n.md` + `docs/arch/locales.md` |
| ビルド構成・同梱バイナリ変更 | `docs/build.md` |
| 翻訳キー追加・変更のみ | ドキュメント更新不要（キー一覧は記載しない方針） |
| テスト方針・スコープ変更 | `docs/testing/policy.md` + `pyproject.toml` の `[tool.coverage.run] omit` / `[tool.pytest.ini_options] markers` |
| テスト対象モジュール追加 | `tests/test_{module}.py` 新規 + `docs/testing/policy.md` のスコープ表更新 |
| リファクタリング（振る舞い不変） | 該当 `arch/{module}.md` のみ（必要に応じて） |
| エージェント / スキルの追加・変更 (`.claude/agents/` `.claude/skills/`) | 該当 `.claude/` 定義 + `docs/git-workflow.md` §5.2（エージェント表）/ §5.3（スキル表）を更新 |
| hooks の追加・変更 (`.claude/hooks/` `.claude/settings.json` の `hooks`) | 該当 hook 実装 + `docs/git-workflow.md` §5.6（hook 一覧）と該当ルール節（例: main 直コミット禁止は §1）を更新 + `tests/test_{hook 名}.py` + `docs/testing/policy.md` のスコープ表 |
| ルールの追加・変更 (`.claude/rules/`) | 該当 rule + `docs/git-workflow.md` §5.4（rule 表）。rule は正本の要点だけを持つので、正本側（例: `harness.md` なら `docs/testing/policy.md` §2.6・§8）を先に直す |
| 権限ルールの変更 (`.claude/settings.json` の `permissions`) | `docs/git-workflow.md` §5.7（allow / 都度確認の分類表）を更新 |
| レビューゲートのモード変更（evaluator / design-review） | `CLAUDE.md` の該当行**のみ**（値の正本。`docs/git-workflow.md` §5.2 は定義であって値ではないので変更不要。skill も参照側なので触らない） |

### 4.2 タスク完了時の手順

archive 移動は**タスクを完結させる実装 PR に同梱するのを原則**とする（専用 PR を立てない。#222）。

1. コード変更 + 対応ドキュメント更新を同一の作業範囲で完了させる
2. `docs/task/{slug}.md` を `docs/task/archive/` へ移動する
3. `docs/task/index.md` の「タスク」表から該当行を削除する
4. `docs/task/archive/index.md` の該当テーマ表に概要 + 更新日を追記し、概要セルの**末尾**に**メトリクス 1 句**を書く（`メトリクス: コミット N（PR #M）・訂正ログ K 件・evaluator J 巡`。算出元と N・K・J の定義は [`/finish-task`](../.claude/skills/finish-task/SKILL.md) C-4。費用の見える化で、後からハーネスを見直すとき（[git-workflow.md](git-workflow.md) §5.9）の情報源になる）

> **単一 PR で完結する小タスクの特例**: 着手から完結までが 1 ブランチ・1 PR に収まり、途中経過を `docs/task/index.md` に載せる意味がない場合は、タスクメモを `docs/task/archive/` に**直接**作成してよい（step 2〜3 の移動・「タスク」表からの削除は不要。step 4 の archive index 追記は必須。対応する Issue が「起票済み・未着手の Issue」表にある場合はその行の削除も同 PR で行う）。

タスクが複数 PR にまたがる場合は**最後の PR** に同梱する。同梱できなかった場合の補完として、複数タスク分をまとめた docs ブランチ + PR（`/finish-task`）で後追い処理してよい。
