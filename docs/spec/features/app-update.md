# アプリ本体（yt-gui）の更新チェック・通知

yt-gui 本体はポータブル zip / AppImage で配布しており（インストーラ・コード署名
なし）、ユーザーが新版のリリースに気づく手段がない。アプリ本体の更新に気づける
よう、**Phase A: 更新チェック＋通知**を提供する。

本仕様は Issue [#198](https://github.com/f8924919/yt-gui/issues/198) に基づく。
実体の自動更新（Phase B）は方式調査
（[research/app-update.md](../../research/app-update.md)）で「GitHub Releases
＋ Sigstore attestation 検証」の自前方式に決定済みで、実装 Issue
[#252](https://github.com/f8924919/yt-gui/issues/252) /
[#253](https://github.com/f8924919/yt-gui/issues/253) で扱う。
設計の意図・接続点は [arch/app_update.md](../../arch/app_update.md) を参照。

## 照会先（データソース）

- 最新版は **GitHub Releases API**
  （`https://api.github.com/repos/f8924919/yt-gui/releases/latest` の `tag_name`）
  を正とする。リリースは `v{version}` タグ（例 `v0.4.0`）で発行される
  （[build.md](../../build.md) のリリース自動化）。
- `releases/latest` は **draft / prerelease を返さない** GitHub API の仕様に
  依拠する。prerelease を更新対象にする要件が出た場合は別途検討する。裏返しと
  して、リリース未発行または全リリースが draft / prerelease のみの場合は
  404 が返り「照会失敗」として扱われる。
- 取得は stdlib `urllib`（タイムアウト 10 秒）。GitHub API は **User-Agent
  ヘッダー必須**のため付与する。未認証の rate limit は 60 req/h だが、
  照会は 1 起動 1 回のためデスクトップアプリの起動頻度では実用上問題ない
  （失敗はサイレントのため実害もない）。

## 比較

- `tag_name` から `v` prefix を除去し、`packaging.version` で現バージョン
  （`yt_gui.get_version()`、[build.md](../../build.md) の単一ソース設計）と
  比較する。
- タグ解析失敗（`v` prefix なし・バージョンとして不正 等）は「照会失敗」として
  扱い、例外を UI 層へ漏らさない。
- 現バージョンが `"unknown"`（パッケージメタデータ未解決。開発環境等）の場合、
  自動チェックはスキップし、手動チェックは「照会失敗」として扱う。
- 開発版バージョン（例 `0.4.0.dev1`）は `packaging.version` の規則上、対応する
  リリース版（`0.4.0`）より古いと判定され「更新あり」通知が出うる。開発時のみの
  挙動で配布物には影響しないため許容する。

## 起動時自動チェック

yt-dlp 更新（[yt-dlp-update.md](yt-dlp-update.md)）の「明示操作起点のみ」とは
**意図的に方針を変え**、起動時の自動チェックを既定で行う。アプリ本体の更新は
気づきにくく通知価値が高いためで、プライバシー配慮はオプトアウト設定で担保する。

- 起動時にバックグラウンドで 1 回チェックする（頻度制御なし＝毎起動。
  起動をブロックしない）。
- **新版検出時のみ**、メインウィンドウ表示後に `QMessageBox` で通知する。
  「リリースページを開く」ボタンで yt-gui の GitHub releases
  （`https://github.com/f8924919/yt-gui/releases`）を既定ブラウザで開く。
- 照会失敗時・最新時は**サイレント**（ダイアログを出さない・起動を妨げない）。
- 他の起動時ダイアログ（依存バイナリ欠落警告等）と同一起動で重なった場合は
  順に表示される（新版検出は稀のため許容する）。
- 設定「起動時に yt-gui の更新を確認する」（既定オン、
  [設定管理](../settings.md)）でオプトアウトできる。本設定は**起動時自動
  チェックのみ**を制御し、下記の手動チェックは設定に関わらず常に利用可能。

## 手動チェック（バージョン情報ダイアログ）

- 既存の「バージョン情報」ダイアログ（[yt-dlp-update.md](yt-dlp-update.md) の
  UI 配置）に、**「yt-gui の更新を確認」ボタン**を追加する。あわせて既存の
  「更新を確認」（yt-dlp 用）は**「yt-dlp の更新を確認」へ改称**し、どちらの
  更新かを対称に示す。
- 押下時の結果表示は yt-dlp 用と対称の 3 分岐。
  - 最新: 情報メッセージ「yt-gui は最新です」。
  - 更新あり: 「より新しい yt-gui (X) があります」＋「リリースページを開く」
    ボタン。
  - 照会失敗（オフライン・HTTP エラー・タグ解析失敗・現バージョン
    `"unknown"`）: 警告メッセージで穏当に通知し、アプリ動作は継続する。
- 文言はすべて [i18n](../i18n.md) の翻訳キー経由で提供する。

## Phase B: 実体の自動更新（Windows のみ・手動適用のみ）

方式は「GitHub Releases のフル zip ＋ Sigstore attestation のアプリ内検証」
の自前アップデータ（比較検討・決定の経緯と設計詳細は
[research/app-update.md](../../research/app-update.md)）。コア（DL・検証・展開）は
[#252](https://github.com/f8924919/yt-gui/issues/252)、適用（差し替え・UI）は
[#253](https://github.com/f8924919/yt-gui/issues/253)。実装の意図・接続点は
[arch/self_update.md](../../arch/self_update.md) を参照。

### 「更新して再起動」の表示条件（プリフライト）

新版検出ダイアログ（起動時・手動チェック共通）に「更新して再起動」ボタンを
追加する。ボタンは次を**すべて**満たすときだけ表示する。

- Windows である。
- PyInstaller バンドルとして実行中（frozen）で、現バージョンが解決済み
  （`"unknown"` でない。開発環境では表示しない）。
- インストール先の**親ディレクトリ**へ書き込み可能（一時ファイルの作成・削除で
  判定。Program Files 配置等の書き込み不可環境では表示せず、UAC 昇格は
  行わない）。
- 展開後の差し替えは親ディレクトリでのフォルダ rename で行うため、判定対象は
  インストール先自身ではなく親ディレクトリである。

非表示のときは従来どおり「リリースページを開く」のみを提示する（手動
ダウンロードへのフォールバック）。

**ダウンロードキュー実行中**は、ボタンを表示するが**無効化**し、キュー完了後に
再度実行するよう案内する文言を本文に添える（yt-dlp / ffmpeg がインストール先の
exe をロックしているため）。判定はダイアログ表示時点の静的判定とする。

### 適用フロー

1. 押下で**モーダル**の進捗ダイアログ（キャンセル可）を表示し、バックグラウンド
   でダウンロード → attestation 検証 → ステージング展開を行う（コアは #252 の
   `self_update`。fail-closed: 検証が通るまで既存インストールへ一切触れない）。
2. ステージング先は**インストール先と同じ親ディレクトリ**の
   `{インストール先名}.update-staging`（同一ボリューム rename の保証。%TEMP%
   不可）。前回失敗の残骸が同名で残っていれば開始時に削除する。
3. 展開結果のルートに実行ファイル（yt-gui.exe）が存在することを確認する
   （存在しなければ差し替えに進まず「更新失敗」扱い）。
4. 成功時: 差し替えスクリプト（PowerShell）を対象ツリー外（%TEMP%）へ書き出して
   `powershell.exe -NoProfile -ExecutionPolicy Bypass` で起動し、アプリを
   終了する。スクリプトの**起動自体に失敗**した場合はアプリを終了せず
   「更新失敗」通知へ戻す。また、検証完了とキャンセル操作が競合した場合に
   備え、スクリプト起動・終了に踏み切る直前にキャンセル状態を再確認する
   （キャンセル済みなら適用しない）。スクリプトの手順:
   1. 旧プロセス PID の消滅を待機（**タイムアウト付き**。PID 再利用の誤検知を
      避けるためプロセス名も併せて照合する。タイムアウト時はインストール先に
      触れず終了）。
   2. 既存の `.bak` があれば削除（1 世代のみ保持）。
   3. 旧フォルダ → `{インストール先名}.bak` へ rename。
   4. ステージング内の新フォルダ → 旧パスへ rename。
   5. 新 exe を起動し、ステージング残骸を削除、スクリプト自身を削除。
   - rename は AV / OneDrive の一時ロックを想定し**指数バックオフでリトライ**する。
5. 手順 3〜4 の途中失敗時は `.bak` を書き戻す**ロールバック**を行い（既存
   インストールを復旧）、復旧した旧 exe を再起動する（バージョンが変わらない
   ことが失敗の実質的な通知となる）。ロールバックも失敗した場合（二重失敗）は
   `.bak`・ステージングを残したまま、OS のメッセージボックスで `.bak` の場所と
   手動復旧を案内する。
6. 新 exe の**起動失敗は差し替え結果に影響しない**（配置は完了しており、手動で
   起動できる。ロールバックしない）。

### 失敗時の通知（fail-closed）

- 検証失敗・attestation なし・ダウンロード失敗・アセットなし等: 「更新に失敗
  しました」を穏当に通知し、「リリースページを開く」導線を案内する。既存
  インストールは一切変更されない。
- ユーザーによる**キャンセル**: 通知を出さずダイアログを閉じる。一時ファイルは
  残さない。

### `.bak`・ステージング残骸のライフサイクル

- 旧版の退避フォルダ `{インストール先名}.bak` は **1 世代のみ**保持する。
- **次回起動のメインウィンドウ表示後**にバックグラウンドで削除する（簡易
  ヘルスチェック: 新版が起動直後にクラッシュした場合は `.bak` が残り、手動で
  復旧できる）。
- 同じタイミングで、過去の失敗で残ったステージングフォルダ
  （`{インストール先名}.update-staging`）も**無条件に削除**する（起動時点で
  常に不要のため。数百 MB の残留を防ぐ）。
- 削除失敗（ロック・権限等）は**サイレントに次回起動へ持ち越し**、起動を
  妨げない。

### 既知の制限

- **多重起動は対象外**: 同一インストール先の exe を複数プロセスで起動している
  場合、差し替えスクリプトの PID 待機は更新を起動したプロセスしか見ないため
  rename に失敗しうる。この場合もリトライ → ロールバックで fail-closed に落ち、
  インストールは壊れない。
- GPO で PowerShell の ExecutionPolicy を強制する企業環境では適用できない
  （`-ExecutionPolicy Bypass` が MachinePolicy を上書きできないため。手動
  ダウンロード導線は残る）。
- 差し替えスクリプト自体が「旧 → `.bak` rename 成功後・新配置前」の瞬間に
  異常終了（電源断・タスク kill 等）した場合、インストールパスが空になる
  残存リスクがある（窓は極小）。この場合も `.bak` に旧版全体が残っており、
  手動 rename で復旧できる。
- macOS / Linux は Phase A（通知のみ）を継続する（macOS の実体更新はコード署名
  [#39](https://github.com/f8924919/yt-gui/issues/39) の後に再検討）。
