# リポジトリ public 化と実メール露出 調査レポート

[← 研究メモ目次](.)

> 本メモは、yt-gui（`f8924919/yt-gui`）を public 化する際に問題となる **コミット履歴へ焼き込まれた実メール
> アドレス（以下 `<実メール>` と表記。個人用メールアドレス）の露出** について、調査結果・履歴書き換えのリスク・
> 実行計画の草案をまとめる。**現時点の方針は「private 維持・public 化は提案しない」**（2026-05-30 にユーザーが
> 判断）。本メモは将来の再検討に備えた検討材料であり、実行を決定したものではない。
>
> **注記**: 本レポートは public 化検討の素材であり、リポジトリ公開時にそのまま公開され得るため、保護対象である
> 実メールアドレスそのものは記載せず `<実メール>` というプレースホルダで参照する。実値は git 履歴の
> author/committer フィールドで確認すること。

---

## 0. 結論サマリ

- 実メール `<実メール>` は **コミットの author/committer メタデータに 166 件** 焼き込まれている。
  ファイル本文・コミットメッセージ本文・タグには露出していない。
- 過去に削除したマージ済みブランチのコミットも、すべて `main` から到達可能な状態で履歴に残っているため、
  **履歴書き換え（`main` / `--all` 対象）を行えば 166 件すべてが書き換わる**。削除による取りこぼしはない。
- ただし履歴書き換えは **全コミット SHA の変更** を伴い、既存 Issue/PR のコミット参照断絶・古いコミットの
  GitHub 側残存・ローカル/fork への旧メール残留という副作用がある。これが 5/30 に書き換えを見送った理由。
- public 化が要件化した場合の実行計画草案を §4 に示す。コストとリスクを許容できるなら実行可能。

## 1. 背景

private を維持している直接の理由は、リポジトリの機能不足ではなく **プライバシー保護（実メール非公開）** である。

- 2026-05-30、ユーザーが「public 化しない」を選択。理由はコミット履歴に焼き込まれた実メール `<実メール>` を
  公開したくないため。
- 履歴書き換えによる除去案も検討したが、Issue/PR スレッドの参照断絶・旧コミット残存リスクから見送った。
- public が前提の機能（GitHub artifact attestation / SLSA provenance, `actions/attest-build-provenance`）は
  個人所有 private では利用不可のため、`release.yml` で `if: ${{ !github.event.repository.private }}` により
  スキップする運用とした（Issue #46 / PR #47）。public 化すれば自動で復活する。
- 以降の新規コミットは実メールを焼き込まないよう、ローカル `user.email` を noreply
  （`44728840+f8924919@users.noreply.github.com`）に設定済み。

## 2. 調査結果（事実確認）

`git log --all` 等で全履歴を実走査した結果。

### 2.1 メール露出の分布

| author \| committer の組 | コミット数 | 区分 |
|---|---|---|
| `<実メール>` \| `<実メール>` | **166** | **実メール（要対処）** |
| `…@users.noreply.github.com` \| `noreply@github.com` | 33 | GitHub 経由マージ等（安全） |
| `…@users.noreply.github.com` \| `…@users.noreply.github.com` | 1 | noreply 設定後の新規コミット（安全） |

- `main` の総コミット数: **200**（期間: 2026-05-02 〜 2026-05-31）。うち 166 が実メール入り。
- 最新の `3e9a8e2`（#46）まで含め、ごく最近のコミットも実メールが残っている（noreply 設定は途中から）。

### 2.2 露出していない箇所（確認済み・問題なし）

- **コミットメッセージ本文 / trailer**（`Co-authored-by` 等）— 実メール文字列の混入なし。
- **追跡ファイルの中身**（ソース・docs・設定）— 実メール文字列・ユーザー名付きアドレスの混入なし。
- **タグ `v0.1.0` / `v0.1.1` / `v0.1.2`** — いずれも author=noreply・committer=GitHub。実メールなし
  （annotated ではなく GitHub Release 由来のコミット参照）。

### 2.3 削除済みブランチのコミットの所在

セッション中にマージ済みローカル/リモートブランチ（`bugfix/46`, `feature/32`〜`42`, `chore/*`, `docs/*` 等
計 12 本）を削除済み。これらが書き換え対象から漏れないかを検証した。

- 本リポジトリの PR は **すべてマージコミット方式**（`Merge pull request #NN …`）でマージされていた。
  そのため各ブランチの個別コミットは merge コミットの第2親としてぶら下がり、**`main` から到達可能**。
- ブランチ削除は **ref（ラベル）を消しただけ** で、コミット実体は `main` の履歴 DAG に残存。

| 観点 | 値 |
|---|---|
| 実メール入りコミット総数（全 ref / `--all`） | 166 |
| うち `main` から到達できる数 | **166** |
| `main` から到達できない（削除で孤立した）数 | **0** |

→ **`main`（= `--all`）を対象に書き換えれば、削除済みブランチ由来を含む 166 件すべてが書き換わる。**

> 注: もし squash マージだった場合は、ブランチの個別コミットが `main` から到達できず孤立し、`--all` でも
> 書き換え対象から外れる逆ケースが起こり得る。本リポジトリは全てマージコミット方式のため該当しない。

## 3. 履歴を書き換えた場合の今後の開発へのリスク

メール置換自体は 166 件を網羅できるが、**「書き換えれば即 public 化して安全」ではない**。主なリスクを挙げる。

### 3.1 全コミット SHA の変更に伴う参照断絶（影響: 大）

- 書き換えると **全 200 コミットの SHA が変わる**（mailmap 置換でも親チェーンが変わるため下流すべて再計算）。
- 既存の **Issue / PR 本文・コメントが参照している旧 SHA がデッドリンク化**する。GitHub の PR は
  「マージ済み」表示や diff が旧コミットに紐づくため、表示が壊れる/たどれなくなる可能性。
- タグ（`v0.1.x`）も貼り直しが必要。Release に紐づくタグの付け替えは Release 表示へ影響し得る。
- ローカルの作業ツリー・既存クローンは旧履歴のままになり、`git pull` では解消せず **rebase / 再クローンが必須**。

### 3.2 旧コミットの GitHub 側残存（影響: 中〜大、public 化の主目的を損なう）

- フォースプッシュ後も、**到達不能になった旧コミットは GitHub 上で即時には消えない**。古い SHA を直接
  指定すれば一定期間アクセス可能（`https://github.com/.../commit/<旧SHA>`）。
- **PR の diff / コメントのキャッシュ**に旧コミット（=旧メール）が残ることがある。
- 完全な消去には **GitHub サポートへの GC 依頼** が必要になる場合がある（保証された即時手段ではない）。
- 既に **fork やローカルクローンが存在すれば、そちらの旧メールは消せない**（今回は private のため外部 fork の
  可能性は低いが、CI キャッシュ・アーティファクト等は別途確認が必要）。

### 3.3 開発フロー・自動化への影響（影響: 中）

- 進行中ブランチがある状態で書き換えると、**全ブランチの rebase / 再作成** が必要。書き換えは
  「未マージ作業が無いタイミング」で行うのが必須（現状 `main` のみなので好機ではある）。
- `release.yml` 等は SHA 依存ではないため Workflow 自体への直接影響は小さいが、**過去 Release / タグの
  再生成** を伴う場合はビルド成果物の再アップロード判断が必要。
- public 化に伴い attestation ガード（§1）が外れて SLSA provenance が復活する。これは利点だが、
  **public 化後はリポジトリ情報・Actions ログが公開**される点も併せて確認が必要（秘匿情報の混入確認）。

### 3.4 メール置換の取りこぼしリスク（影響: 小、対策可能）

- author と committer の両方を置換対象にする必要がある（166 件は両方が実メールだが、混在ケースに備える）。
- `.mailmap` だけでは表示上の置換に留まる場合があるため、**履歴自体を書き換える**（`git filter-repo`）必要。

## 4. 実行計画 草案（public 化を決定した場合）

> 未確定の草案。実行前に「過去 Release / Issue・PR 参照の扱い」をユーザーと合意すること。

### 前提・準備

1. **完全バックアップ**: `git clone --mirror` でリポジトリ全体（全 ref）をローカル保全。元に戻せる状態を確保。
2. 未マージの作業ブランチが無いことを確認（現状 `main` のみ＝好機）。
3. 置換後メールを決定（推奨: `44728840+f8924919@users.noreply.github.com`。GitHub の noreply 形式）。

### 書き換え手順（`git filter-repo`）

4. `git filter-repo` を導入（`uv tool install git-filter-repo` 等）。
5. mailmap を用意（`<実メール>` は実際の旧アドレスに置き換える。**このファイルはコミットしない**）:

   ```
   # mailmap.txt （新表示名 <新メール> <旧メール>）
   f8924919 <44728840+f8924919@users.noreply.github.com> <実メール>
   ```

6. 書き換え実行（author/committer 両方を置換）:

   ```bash
   git filter-repo --mailmap mailmap.txt
   ```

   - 補足: 名前ごと正規化したい場合や mailmap で漏れる場合は `--commit-callback` で
     `commit.author_email` / `commit.committer_email` を直接置換する方式に切替。

7. 検証（`OLD_EMAIL` に実際の旧アドレスを設定して実行）:

   ```bash
   OLD_EMAIL='（実際の旧アドレス）'
   git log --all --format='%ae %ce' | grep -ciF "$OLD_EMAIL"   # → 0 を確認
   git log --all --format='%ae %ce' | sort | uniq -c           # noreply に統一されたか確認
   ```

### 反映・後処理

8. リモート再接続とフォースプッシュ（`filter-repo` は origin を外すため再追加が必要）:

   ```bash
   git remote add origin https://github.com/f8924919/yt-gui.git
   git push --force --all
   git push --force --tags
   ```

9. **タグ・Release の確認/貼り直し**（`v0.1.0`〜`v0.1.2`）。Release が旧タグ commit を指す場合は再作成を検討。
10. **public 化**（`gh repo edit f8924919/yt-gui --visibility public`）。`release.yml` の attestation ガードは
    残置で問題ない（public 時は自動で attest ステップが走る）。
11. **旧コミットの GC 依頼**: 必要なら GitHub サポートへ到達不能コミットの削除を依頼。
12. public 化後チェック: Actions ログ・Issue/PR・Wiki 等に秘匿情報や旧メールが残っていないか最終確認。

### ロールバック

- 問題があれば §4-1 の mirror から復元してフォースプッシュで巻き戻す（ただし他者が既に新履歴を取得していると
  巻き戻しは困難になるため、合意・周知のうえ短時間で完結させる）。

---

## 5. 推奨

- **当面は private 維持が妥当**。public 化の動機（attestation 復活・OSS 公開など）が明確になるまで、書き換えの
  コスト（参照断絶・旧コミット残存対応）に見合わない。
- public 化が要件化した場合は、§4 を「**未マージ作業が無いタイミング（現状の `main` 単独状態が好機）**」に実施し、
  旧コミット残存の後処理（§3.2）まで含めて一括で完了させる。
- いずれにせよ、新規コミットへの実メール混入は noreply 設定で既に止血済み（§1）。**実メール入りは過去 166 件で
  打ち止め**であり、放置しても増えはしない。
