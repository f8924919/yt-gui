# 測定器（テスト・hook・検証の判定）編集時のルール

次のものは、どれも「これを足したから今後は検出できる / 止められる」と言う**測定器**であり、壊れた測定器は red ではなく**偽 PASS**を出す。記述ルールの**正本は [docs/testing/policy.md](../../docs/testing/policy.md) §2.6・§8**。本ファイルは編集時に思い出すべき要点のみで、詳細はコピーしない（drift 防止。[git-workflow.md](../../docs/git-workflow.md) §5.4）。テストファーストと red の単独コミット禁止は [testing.md](testing.md) の担当（`tests/` では両方が載る。役目が違うので重なりは許している）。

- `tests/` のテスト
- `.claude/hooks/` の hook と、それを登録する `.claude/settings.json`（matcher や入力キーを誤ると、hook は**何も言わずに**何もしなくなる — #285 の `NotebookEdit` の素通り）
- `scripts/download_binaries.py` の sha256 検証（合わなければ止まる判定。偽 PASS になったときの害が最も大きい）
- `.github/workflows/` の CI ゲート（ステップが走っていない・終了コードを握りつぶしている形は、green のまま何も見ていない）

## コミット前に必ず出すもの（policy §8.1）

1. **赤を先に見て記録する**（A1）: 判定ロジックを足した／変えたら、green をコミットしてから対象を壊し、red になるログを取る。テストファーストの新しいテストは、実装前の FAILED 行でよい（§2.6）。**壊す前（または実装前）のコミット hash と一緒に、タスクメモか PR 本文に貼る**（scratchpad に置いたままにしない。`evaluator` は貼られていなければ ❌ にする）。
   - **変異の作業が失敗した回は死亡と数えない**（fail-closed）: 変異が当たらなかった・テストが起動しない・収集が 0 件なら、red ではなくハーネスの失敗として止める。
   - **「N/N 撃墜」で満足しない。** 変異が別の場所に当たっていたり、対象のテストに到達する前に落ちていたりしても「死亡」と出る。**各変異で落ちたテスト名を表にし、狙ったテストが含まれているかを見る**。
2. **終了コードだけで判定しない**（A2）: hook の「通す」と「フェイルオープンで通す」はどちらも無出力・exit 0 になる。分岐ごとに別のテストで、出力の**内容**まで見る。
3. **実物と突き合わせる**（A3）: 合成データだけの期待値は検査対象と同じ誤解を共有しうる。実物（実際の `docs/task/index.md` 等）を読むテストを 1 本置く。
4. **変異させたら必ず戻す**（A4・A7）: 手で壊すなら、壊す前にコミットし、`git checkout -- <file>` で戻して `git diff --quiet -- <file>` で確かめてから次の変異へ。自動化するならコピーを変異させ、無変異のコピーが green になることを先に見る。
5. **黙らない**（A5）: 判定できない・読めないときにフェイルオープンで通すのはよいが、通したことが誰にも見えない形にしない（git-workflow §5.6「フェイルオープンでも黙らない」）。
6. **足したテストが本当に走っているか**（A6・pytest 収集）: `tests/test_*.py`・`test_` で始まる関数の名前にし、`pytest -q -rs` で **passed に数えられている**（skip / deselect されていない）ことを確かめる。
7. **検査対象の列挙を疑う**（A8）: 対象が意図した集合になっているか、0 件でないかを確かめる（green は「問題が無い」ではなく「見ていない」かもしれない）。
8. **同じ事実を 2 か所に書かない**（A9）: 件数・既定値・出力書式は正本 1 か所に置き、他所ではリンクする。**コードのコメントに実測値を書かない**。
9. **測っている間に足元を動かさない**（A10）: 評価・測定の前後で `HEAD` と作業ツリーが変わっていたら、結果ではなく前提の不備として測り直す。
